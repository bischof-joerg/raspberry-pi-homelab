5. Verify the Public Key Fingerprint
Use this check in pre-commit, CI, deploy, and backup scripts:
expected_fpr="$(tr -d '[:space:]' < config/backup/homelab-backup-recovery-public.fingerprint)"
actual_fpr="$(
  gpg --show-keys --with-colons config/backup/homelab-backup-recovery-public.asc \
    | awk -F: '$1 == "fpr" { print $10; exit }'
)"

if [ "$actual_fpr" != "$expected_fpr" ]; then
  echo "ERROR: backup public key fingerprint mismatch" >&2
  echo "Expected: $expected_fpr" >&2
  echo "Actual:   $actual_fpr" >&2
  exit 1
fi
Any mismatch is a security failure. It means future backups may be encrypted to the wrong recipient.

Service Definition of Done (DoD) Template
(Optimized for IaC with Docker Compose + VictoriaMetrics)
ASCII-only, Markdown-friendly
Goal:
- This Definition of Done focuses ONLY on aspects that are NOT automatically
  guaranteed by Docker Compose or basic IaC usage.
- Items that are inherently handled by Compose (container existence, basic
  lifecycle, declarative config storage) are intentionally omitted.
- The template remains class-based to reduce overhead for small services.
- Observability stack specifics are aligned to VictoriaMetrics components.
- Alertmanager is still used for alert routing and notifications.
----------------------------------------------------------------------
1. Service Classification (Mandatory)
----------------------------------------------------------------------
Each service MUST declare exactly one value per dimension.
1.1 State Model
- stateful        : persists data that must survive restarts
- stateless       : no persistent data
1.2 Exposure Model
- public-ingress  : reachable via reverse proxy / external network
- internal-only   : reachable only inside internal Docker networks
1.3 Criticality
- critical        : outage affects multiple services or core functionality
- non-critical    : isolated or convenience service
Optional (informational):
- Runtime role    : core | monitoring | application
Example:
- State model    : stateful
- Exposure model : public-ingress
- Criticality    : critical
----------------------------------------------------------------------
2. Source of Truth & Documentation
----------------------------------------------------------------------
Applies to ALL services.
[M] Service documentation exists at docs/services/<service>.md.
[M] Documentation matches the deployed configuration.
[M] Any deviation from standards is explicitly documented and justified.
VictoriaMetrics-specific additions (where applicable):
[M] If the service participates in metrics/logs/alerts, documentation includes:
    - which component scrapes/sends data (vmagent, direct remote_write, etc.)
    - which backend stores/queries it (victoriametrics, victorialogs)
    - which alerting path is used (vmalert -> alertmanager)
----------------------------------------------------------------------
3. Versioning & Update Policy
----------------------------------------------------------------------
Applies to ALL services.
[M] Image version is pinned (no "latest").
[M] Update mechanism is defined (e.g. Renovate rule).
[M] Upgrade and rollback steps are documented.
[O] Image pinned by digest (recommended for critical services).
VictoriaMetrics-specific additions (where applicable):
[M] Version compatibility between related components is documented:
    - vmagent <-> victoriametrics (remote_write / query)
    - vmalert <-> victoriametrics (rule evaluation datasource)
    - vmalert <-> alertmanager (notification routing)
----------------------------------------------------------------------
4. Secrets & Configuration Injection
----------------------------------------------------------------------
Applies to ALL services.
[M] No secrets are stored in Git.
[M] Secret injection mechanism is documented (env file on disk, secret store,
    runtime injection).
[M] Required secrets are listed by name (without values) in documentation.
VictoriaMetrics-specific additions (where applicable):
[M] If auth is used for ingestion/query:
    - credentials/tokens are injected via secrets mechanism
    - endpoints requiring auth are documented (remote_write, query, logs ingest)
[M] If Alertmanager webhook/receiver secrets exist, they are documented by name.
----------------------------------------------------------------------
5. Data & Persistence
----------------------------------------------------------------------
stateful services ONLY:
[M] Persistent data paths/volumes are documented.
[M] Backup strategy is implemented (tool, schedule, retention).
[M] Restore procedure is documented.
[M] At least one restore test has been executed successfully.
[M] RPO/RTO expectations are documented.
stateless services:
[M] Service is explicitly documented as stateless.
[N/A] Backups and restore procedures.
VictoriaMetrics-specific guidance (where applicable):
- victoriametrics: typically stateful (metrics storage).
- victorialogs: typically stateful (logs storage).
- vmagent: typically stateless (scraper/forwarder), but may keep small buffers;
  if persistent queues/buffers are enabled, document volume usage and recovery.
- vmalert: typically stateless (rules + evaluation), but may store state;
  document if any local state is configured.
- alertmanager: stateful if it stores silences/inhibition state; document volume.
----------------------------------------------------------------------
6. Exposure, Access & Trust Boundaries
----------------------------------------------------------------------
public-ingress services:
[M] External URL(s) documented.
[M] TLS is enforced via ingress.
[M] Authentication and authorization model documented (or explicitly "none").
[M] Admin or management endpoints are protected or restricted.
internal-only services:
[M] Service is documented as internal-only.
[M] Trust relationship to consuming services is documented.
VictoriaMetrics-specific additions (where applicable):
[M] For each ingest/query endpoint, document:
    - who can reach it (networks, clients)
    - whether it is internal-only or proxied via ingress
    - whether auth is required
[M] For logs ingestion (victorialogs), document allowed senders and protocol.
----------------------------------------------------------------------
7. Observability (What Humans Need, Not What Compose Gives)
----------------------------------------------------------------------
Applies to ALL services.
[M] Logs are accessible via the central logging system.
[M] A clear health signal exists and is documented
    (health endpoint, status page, or functional check).
critical services:
[M] Meaningful metrics are exposed and collected (where applicable).
[M] At least one Grafana dashboard exists.
[M] Alerts exist for:
    - service unavailable
    - unhealthy state
[M] Alert routing has been verified at least once.
non-critical services:
[O] Metrics and dashboards.
[O] Alerts (recommended if user-facing).
VictoriaMetrics-specific mapping:
- Metrics collection is performed by vmagent (scrape) and stored in victoriametrics.
- Alert evaluation is performed by vmalert.
- Notification routing is handled by alertmanager (still used).
- Logs are stored in victorialogs and queried from Grafana via datasource.
Mandatory details for monitoring components:
[M] If the service is monitored by vmagent, documentation includes:
    - scrape job name and target labels (stable identifiers)
    - expected key metrics (at least 3) and how to interpret them
[M] If alerts exist in vmalert, documentation includes:
    - rule group name(s)
    - alert name(s)
    - runbook link(s)
[M] If Alertmanager routes are used, documentation includes:
    - route name/receiver name (no secrets)
    - notification channel (e.g. email, webhook) and test procedure
----------------------------------------------------------------------
8. Security & Hardening (Beyond Defaults)
----------------------------------------------------------------------
Applies to ALL services.
[M] Service threat surface is documented:
    - public vs internal
    - user-facing vs machine-facing
[M] Any elevated privileges or exceptions are documented and justified.
public-ingress services:
[M] TLS certificate lifecycle verified.
[M] Rate limiting / abuse protection documented (even if delegated to ingress).
critical services:
[M] CI vulnerability scan results reviewed and accepted.
[O] Additional hardening documented (seccomp, apparmor, read-only FS, etc.).
VictoriaMetrics-specific additions (where applicable):
[M] If ingest/query endpoints are exposed beyond internal networks:
    - require auth OR network allowlisting is documented and enforced
[M] If multi-tenant separation is required, document the strategy
    (labels/tenants/endpoints) and enforcement points.
----------------------------------------------------------------------

----------------------------------------------------------------------

[M] Service-specific config validation exists where applicable.
Replace Prometheus/Alloy examples with VictoriaMetrics equivalents:

ALL services:
[M] Functional health verification succeeds
    (not just container running, but service usable).
public-ingress services:
[M] Endpoint reachable via ingress.
[M] TLS handshake verified.
stateful services:

critical services:
[M] Monitoring confirms service is UP.
[M] Alert test executed at least once.
VictoriaMetrics-specific post-deploy tests (where applicable):
[M] vmagent successfully scrapes at least the expected core targets
    (e.g. node-exporter, cadvisor) and remote_writes to victoriametrics.

[M] victorialogs accepts logs (or has recent log entries) and queries succeed.

10. Operations & Lifecycle
----------------------------------------------------------------------
Applies to ALL services.
[M] Start, stop, restart behavior documented.
[M] Upgrade procedure documented.
[M] Rollback procedure documented.
critical services:
[M] Common failure modes documented.
[M] At least one runbook or incident note exists.
VictoriaMetrics-specific operations (where applicable):
[M] Document retention settings and impact:

[M] Document capacity management:

A service is considered DONE when:

Logs werden nicht Verarbeitet: victorialogs einführen. Was ist BestPractice um die Logs zu analysieren? UI? Dashboard?
Hier meine Festlegung:
Lass uns die Umsetzung von VictoriaLogs wie folgt angehen
1. Collector-Auswahl
	- mit Vector
	- Journald-Integration: wenn Docker-Logs auf dem Pi via via Journald laufen, soll der Collector direkt das Systemd-Journal lesen (source type: journald)
	  um doppelte Disk-I/O durch zusätzliche JSON-Log-Files von Docker zu vermeiden.
	- Backpressure Handling: limitiere den Speicher-Buffer, damit der Collector bei Lastspitzen nicht den RAM des Pi 5 füllt.
2. Stream-Felder & Kardinalität
VictoriaLogs unterscheidet strikt zwischen Stream-Feldern (Indizes) und normalen Feldern.
    - Goldene Regel: Nur Felder mit niedriger Kardinalität in _stream_fields aufnehmen.
        Gut: host, stack, service, namespace, container_name.
        Schlecht: ip, user_id, trace_id, timestamp – diese gehören in den Log-Body oder als normale Felder.
    - Ziel: Die Anzahl der aktiven Streams sollte im Tausenderbereich bleiben, um Suchanfragen performant zu halten.
3. "System Gesund" Dashboards & Queries (LogsQL)
	- Logs in den letzten 5 Minuten >0
	- Error-Logs nach Service aggregierbar
	- Ingestion Rate: Überwachung, ob überhaupt Daten ankommen: _time:5m | stats count() as logs_count.
    - Error-Aggregation: Top-Fehlerquellen der letzten Stunde: _time:1h level:error | stats count() by service | sort by count desc.
    - Volume Spike: Unerwarteter Log-Anstieg (Indiz für Loops): _time:1h | stats count() by service, host.
    - Internal Health: VictoriaLogs exportiert selbst Metriken unter /metrics. Scrape diese mit deinem bestehenden vmagent, um vm_rows_added_total oder vm_request_errors_total in Grafana zu sehen.
4. Spezifische Pi 5 / Docker Tipps
    - Storage-Limitierung: Nutze beim Start von VictoriaLogs das Flag -retention.maxDiskSpaceUsageBytes, um zu verhindern, dass Logs deine Festplatte füllen.
    - Resource Limits: Limitiere den VL-Container in der docker-compose.yml (z.B. mem_limit: 2GB), da VictoriaLogs bei großen Queries aggressiv RAM cacht.
